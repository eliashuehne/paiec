Answer given: **use the English checkpoint**. Evidence base is the 10 sample_200
pairs (seed 20261021), zero-shot, `task_correctness_v1`, MLX FP16, compared with

## Reusable measurement technique

Item language composition from `payload/data/<benchmark>/formatted_tables/
items.parquet`, column `content`: count items where >30% of `str.isalpha()`
characters have `ord > 0x0370` and are not punctuation. Reads only the items
table (small), never `traces.parquet` (23.4 GB). Sampling 2000 rows with
`random_state=0` reproduced the fractions above.

Note `configs/benchmarks/*.json` are research notes with
`outcome_meanings`/`question`/`evidence`/`limitations` keys — `helm_afr.json`
still carries its old exact-match question. They are not an active question
registry (see AGENTS.md); do not restore prompt selection by benchmark name.

## Diagnosis: why we are worse than 0.5 (asked 10-22 ~09:40, evidence gathered then)

User: "obviously right now we are doing worse than just predicting 50% each time."
Then authorized "go ahead" for experiment work. Findings I actually measured:

**The baseline gap is real on a bigger sample, and significant.**
- `default` suite (32 pairs, 120 eval items/pair), English/512 zero-shot, run
  `2c83ed48`: mean pair Brier **0.3204** vs 0.2500 for always-0.5. Excess
  **+0.0704**, 95% CI [+0.0376, +0.1024], **t=4.17, p=0.0002**, worse on
  **24/32 pairs**. This is conclusive at this sample size.
- On the smaller `sample_200` (10 pairs), English/1024 run `142e93d8` = 0.2758;
  excess +0.0258, p=0.409 — **NOT distinguishable** from 0.5. So the 10-pair
  suite was too small to establish the very claim we were making. Always quote
  the suite size with any "worse than 0.5" statement.
- Multilingual/1024 on sample_200 = 0.3818, excess +0.1318, p=0.018 (9/10).
- **Minimum detectable effect on 10 pairs is ~0.067 Brier** (sd of pair Brier
  0.0939, t=2.262, df=9, 80% power). That is the number to quote when someone
  asks whether a 10-pair result is meaningful. Anything smaller needs more pairs
  or more items per pair (`default` gives 32 pairs).
- Per-benchmark on `default` (excess over 0.25): editbench +0.154, bbq +0.154,
  ai2d_test +0.119, helm_afr +0.066, afrimedqa +0.062, devbench +0.039,
  cruxeval +0.027, **cmmlu −0.058** (only one better than 0.5).

**Diagnosis: the probabilities are badly miscalibrated, not merely noisy.**
Murphy decomposition on expanded responses (sample_200 budget 0, run 142e93d8):
uncertainty 0.2477, reliability **0.1044**, resolution **0.0386**; check
unc−res+rel = 0.3136 matches actual 0.3132. Reliability dominates resolution —
Laya's spread is mostly noise, and it lacks the resolution to beat a constant.
- Mean predicted 0.604 vs observed base rate 0.650; predictions span 0.153–0.888.
- Mean absolute calibration gap per benchmark on `default`: editbench **0.381**,
  ai2d_test **0.361**, bbq 0.291, helm_afr 0.247, devbench 0.175.

**Discriminative power is near zero.** Pooled item AUC on `default` =
**0.4983**. Per benchmark: cruxeval 0.573, afrimedqa 0.571, ai2d_test 0.547,
helm_afr 0.524, cmmlu 0.514, devbench 0.476, bbq 0.473, editbench 0.447. Only
editbench is even mildly inverted. Earlier "4 benchmarks inverted" read came
from 20-item groups and does not survive at 480 items each — do not repeat it.

**My own errors this session, both caught and corrected:**
1. First AUC function returned **1.0 for all 8 benchmarks**, contradicting raw
   BBQ rows I had just printed (clearly interleaved). Cause: buggy comparison
   logic. Fixed by using the rank statistic
   `(sum(ranks[y==1]) - n1(n1+1)/2)/(n1·n0)`. Always sanity-check a too-perfect
   metric against raw rows before reporting it.
2. Used the `(p−y)²` shortcut on item means, which understates Brier when an
   item has >1 response (20 items have 20 responses each). Correct form expands
   to per-response and gave 0.3132 vs the shortcut's 0.2673. Same class of bug
   as the 10-21 cruxeval 0.0846 scare. **Always expand to per-response.**
3. Reported an in-sample isotonic recalibration (0.1944) that looked great, then
   the honest leave-one-benchmark-out version came out **0.3201 — worse than
   raw**. Killed my own lead. Never quote an in-sample recalibration as a
   headroom estimate.
4. Told the user the cache was a pure duplicate and that 41 benchmarks existed
   only in cache. Partly wrong: cache lists 102 dirs but `prepare_data.log` shows
   **61 eligible** (binary + item granularity) — the other 41 were filtered by
   design and never fully downloaded. Corrected before deleting.
5. My own hand-rolled symlink/blob accounting returned "0.00 GiB" repeatedly.
   `du` and per-directory blob resolution disagree wildly. Use
   `huggingface_hub.scan_cache_dir()` for authoritative numbers.

**Oracle headroom bounds (per-response, sample_200 budget 0):** raw 0.3132,
always-0.5 0.2500, oracle per-benchmark polarity flip 0.2397, oracle global
isotonic 0.2275, oracle per-benchmark isotonic 0.1944. So even perfect
per-benchmark calibration only reaches ~0.194, and that bound is unattainable
out of sample (see error 3). Fixing polarity alone lands at 0.2397 — barely
better than a constant. **Implication: calibration tweaks cannot rescue this;
the signal itself is the problem.**

## Structural finding that shapes all future experiments

**The label budget axis is completely inert in zero-shot.** Predictions at
budgets 0/1/3/7/15/31 are bit-identical (max |diff| = 0.000e+00 across all 200
items) because `use_labels` defaults False, so `build_state` never adds
`revealed_examples`. Consequence: any "budget curve" from a zero-shot run is a
flat line, and the nested budgets 0/1/3/7/15/31 only carry information when
`--laya-use-labels` is on. Do not interpret a flat budget curve as a modelling
result.

**Several benchmarks cannot be solved from the supplied text fields.**
`devbench` requires images (`asset_manifest` 271/271 items, `item_content` is
file references like `lex-lwl/images_donnelly/milk_glass.png`); the text-only
adapter never receives image bytes. `ai2d_test` likewise (3088/3088 items).
Editbench requires executing tests against a generated implementation. So the
input boundary itself caps achievable accuracy on a large share of the suite —
this is a reason to expect calibration-only wins to stay small, not a bug.
