  distinct tensor shape, ~0.78 GB per new batch shape at batch 8, and its default
  `cache_limit` == `memory_limit` == 16.32 GB on a 16 GB Mac whose GPU

  `set_memory_limit` 6 GiB, overrides `PAIEC_MLX_CACHE_LIMIT_GB` /

- Verified: 100-item untrimmed pair → 1.47 GB resident, cache plateaus 2.15 GB;

- Smoke predictions unchanged: MLX FP16 and PyTorch reference both Brier ALC 0.4551 on

## Truncation finding — corrects my earlier claim

- I told the user "221 of 1000 truncated (22%), plausible for devbench/cruxeval".
  That was wrong twice over. Measured with the real tokenizer: **192/1000 = 19.2%**
  are over 512 tokens (the 221 counter counts forward *records*, double-counting
  states shared across budgets). And devbench is 0/100 over 512.
- Real distribution (median / max / over-512): editbench 1556 / 11443 / **89**;
  helm_afr 804 / 3562 / **100**; cruxeval 448 / 515 / 2; afrimedqa 283 / 536 / 1;
  devbench 286 / 313 / 0; bbq 204 / 272 / 0; cmmlu 308 / 509 / 0; ai2d_test 0/200.
  Suite median 296, p99 6330.
- Ceilings: >1024 9.6%, >2048 4.1%, >4096 1.8%, >8192 0.8%.
- Neither checkpoint's docs nor our docs ever claimed 8192; that was my own error.
  Encoder `max_position_embeddings` is 8192, but `rl_agent_config.json` shows the
  english checkpoint was **trained at max_len 512** (head_max_len 192) and
  multilingual at **max_len 1024** (head_max_len 256). Going to 8192 is 16x outside
  the trained distribution.
- Cost is linear in the ceiling because every item pads to `max_len`:
  512→0.47s, 1024→0.95s, 2048→2.14s, 4096→5.45s, 8192→14.25s (3 longest items).
  Batch 8 at 8192 fits (4.29 GB peak, under the 6 GiB guard) so it would not crash,
  just be very slow. 2048 is the defensible ceiling.

## Performance investigation — negative results, don't redo

- The predictor cache is already doing heavy lifting: 17,400 predictions scored but
  only 1,000 forwards = 16,400 eliminated (**94% saved**), bounded LRU at 4096.
  Nothing to add there.
- Length-sorting to cut padding: theory says 1.13x waste at cap 512 and 1.90x at 8192,
  but measured gain was ~1.01x (helm_afr) and 1.06x (cmmlu, uniform lengths); at
  cap 2048 it was 0.94–1.04x, i.e. noise. Encoder cost tracks per-item sequence
  ceiling, not padded positions.
- **Batch size is the opposite of intuition**: batch 1 = 9.5 items/s, 4 = 9.0,
  8 = 8.6, 32 = 8.3. Prefill-only workload, so batching only adds padding. Published
  batching speedups are decode workloads. Batch 8 costs ~10% throughput vs batch 1;
  kept for memory headroom, not speed.

## Timing surprise — English slower than multilingual, explained

- english@512 24.6s, english@1024 32.7s, english@2048 47.2s, all with 200 forwards;
  multilingual@512 9.3s, @1024 12.9s, @2048 18.1s. Initialization identical (0.79s).
- Cause is architecture, not a bug: encoders differ. English = ModernBERT-large
  (hidden 1024, 28 layers, 16 heads, intermediate 2624); multilingual = mmBERT-base
  (hidden 768, 22 layers, 12 heads, intermediate 1152). Both max_position_embeddings 8192.
  So English costs ~2.5-2.7x per item. Documented per-checkpoint cost should say this.
- Also confirms cost is roughly linear in max_len, as the docs now claim.

- **2. Comparison tool.** `src/paiec/compare.py` + `scripts/compare_runs.py`.
  Rebuilds per-pair Brier from `predictions.csv` sufficient statistics
  (`k(1-p)^2 + (w-k)p^2` averaged over responses) — reproduces logged per-pair
  scores to 5e-17 on all 10 sample_200 pairs. Reports summary / paired
  (delta, median, seeded percentile bootstrap CI, two-sided paired t-test,
  wins-losses-ties) / per-benchmark tables; `--csv` writes all three.
- **Trap I hit:** my first reconstruction averaged labels per item instead of
  scoring per response and showed a fake 0.0846 mismatch on cruxeval. Always use
  the response-count weighted form; per-item label means are NOT sufficient.
- Exact-match guard: comparisons refuse unless both runs scored the same item
  IDs (from predictions.csv, not the suite name). `--allow-partial` restricts to
  the shared subset and flags `partial`. Pair-level-only runs (older runs with no
  predictions.csv) are always partial, since item overlap is unverifiable.
- scipy is present in both envs but NOT used: the t-test uses a self-contained
  regularized incomplete beta so the compare module needs only numpy/pandas.
  Tests cross-check against scipy when importable and skip otherwise.
- **141 tests pass in both `.venv-laya-mlx` and `.venv-laya`**; `git diff --check`
  clean. `docs/mlflow.md` gained "Compare runs" and "Dataset inputs";
